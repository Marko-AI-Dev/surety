# AI journey testing for the buyer's chat

13 Nov 2026. Approved by Marko as step 4 of adopting the principles in `AGENTS.md`.

## Why

Unit tests prove the code works. They do not prove a new buyer can find and finish a task. This week's two screen problems (a text box that vanished, a reading pane that opened on the wrong supplier) were found by a person, not by a test.

## What

An AI browser agent (Jev Ultrafast, the same setup Marko used on his previous app) is given one goal in plain words and has to finish it on the running app. The purchase's own record is then checked, so the agent cannot just claim success.

- `journeys/surety_journeys.py`: the journeys and the runner. Each journey is a name, a seed (the state to start from), a goal that names no button, and a check against the record.
- `scripts/practice-backend.ts` (`pnpm practice`): the real API server over an in-memory store with a scripted team. No keys, no ledger, no agents. A control port resets it between runs.
- `journeys/runs/`: one report per run, with the pass rate, median actions and median seconds per journey, and the last steps of every failure.

It is not part of `pnpm check`: it needs a model, a browser and a few cents of credit per run.

## Rules

- The practice backend only. The runner refuses anything else.
- Synthetic data only. The model keys stay in the agent checkout's own git-ignored `.env` and are never printed.
- The runner uses a headless browser of its own with an empty profile, never a person's browser.
- A journey that fails, or needs far more actions than it should, is a design problem to fix in the screen. Do not reword the goal to name a button.
- A new feature ships with a journey.

## How to read a result

High pass rate and a low action count is the aim. The five product measures Marko set on 13 Nov apply here: how fast a new buyer reaches the first "it's working" moment, how much care the first conversation gets, and that no screen ever shows a dead end.

## First run (13 Nov, laptop size, practice backend)

| Journey | Passed | Median actions |
|---|---|---|
| Order solar panels | 0/3 | 12 |
| Order, knowing what matters | 0/3 | 9 |
| Say yes to the deal | 3/3 | 1 |
| Say no to the deal | 3/3 | 1 |
| Ask for the best offer now | 3/3 | 2 |
| Reword a message before it goes | 3/3 | 4 |
| Approve every message first | 3/3 | 2 |

**The finding: the first conversation is where a new buyer gets stuck.** A buyer says what they need in one sentence, and the start button does not appear: the agent asks two more questions first (what matters most, how hard to push). The browser agent never got past them in six tries. Part of that is the agent's own weakness (it kept retyping its first sentence), so this run does not prove a person would be stuck. It does show the first "it's working" moment is three exchanges away when it could be one.

**Proposed fix, not built:** treat "what matters most" and "how hard to push" as defaults (a balance, firmly), show them in "Here is what I understood" where they can be changed, and offer the start button after the first complete sentence. The target is the ordering journey passing 3/3 in about three actions.

Everything after the start is easy to find: yes, no, asking for the best offer, rewording a message and switching to approve-first all pass every time in one to four actions.
